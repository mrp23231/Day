# Day — выпуск первой беты

Это инструкция подготовки и проверки, а не подтверждение опубликованного релиза. Локальная версия работает без сервисных ключей. Облачная бета требует настроенного Supabase, серверных AI-провайдеров для соответствующих функций, размещённого сервера и live-проверок ниже. Проверка наличия переменных не проверяет права, доступность проекта, письма или оплату.

## 1. Воспроизводимая проверка кандидата

Для хостинга используйте поддерживаемую LTS-версию Node.js; Dockerfile использует Node 24. Минимум Next.js — 20.9+, но Node 20 уже EOL на дату этого выпуска ([официальные статусы Node.js](https://nodejs.org/en/about/previous-releases)). Зависимости устанавливаются из `package-lock.json`.

```sh
npm ci
npm run verify
npm audit --omit=dev
npm run release:check
```

`verify` последовательно запускает ESLint, тесты preflight, весь Vitest в одном worker и production build с проверкой TypeScript. Не запускайте одновременно ещё одну сборку или полный набор тестов. Не собирайте `.next` в каталоге работающего production-сервера: используйте отдельный каталог/артефакт, затем переключите релиз.

`release:check` читает production `.env`-файлы через загрузчик установленного Next.js, учитывая приоритет переменных процесса. Выводит только имена переменных и статусы; запросов к сервисам не отправляет. Без `--strict` отсутствующие ключи не блокируют локальную проверку. Ошибка чтения конфигурации возвращает код 1.

Перед публикацией облачной беты:

```sh
npm run release:check -- --strict
```

Строгий режим возвращает код 1 при отсутствующей обязательной конфигурации или некорректном URL/явно серверном публичном ключе. Код 0 означает только прохождение проверки конфигурации. Сохраните журнал проверки, дату, идентификатор/архив исходников, `package-lock.json` и соответствующий production-артефакт. Не прикладывайте ключи, cookies или пользовательские записи к журналу.

## 2. Конфигурация среды

Скопируйте `.env.example` в `.env.local` для локальной работы или задайте значения в секретах хостинга:

| Переменная | Где используется | Требование |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Сервер и браузер | HTTPS URL нужного Supabase-проекта |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Сервер и браузер | Публичный anon/publishable key этого же проекта |
| `SUPABASE_SERVICE_ROLE_KEY` | Только сервер | Ключ администратора для удаления аккаунта |
| `OPENAI_API_KEY` | Только сервер | Day AI chat; ключ проекта с доступом к Responses API |
| `OPENAI_MODEL` | Только сервер | Необязательно; по умолчанию модель из `.env.example` |
| `FOOD_AI_PROVIDER` | Только сервер | `gemini` по умолчанию; `openai` только по явной настройке |
| `GEMINI_API_KEY` | Только сервер | Распознавание еды через Gemini |
| `GEMINI_FOOD_MODEL` | Только сервер | По умолчанию `gemini-3.1-flash-lite`; квота зависит от Google-проекта |

Никогда не помещайте service-role, secret key или ключи AI в `NEXT_PUBLIC_*`. Префикс делает значение доступным браузеру. Публичные переменные встраиваются **во время `next build`**: перед сборкой задайте значения целевой среды; после их изменения пересоберите и перевыпустите приложение. Смена серверных секретов требует обновления среды и перезапуска серверных процессов. Не переносите собранный с тестовым Supabase артефакт в production без пересборки.

## 3. Supabase и реальные аккаунты

По состоянию на 19 ноября 2026 года в проекте `czoybiitgacfpwfuxfak` с явного разрешения применена миграция `day_initial_schema`; 11 таблиц имеют включённый RLS. Email-вход и подтверждение email включены. На 19 ноября Google-провайдер был выключен. После этого пользователь самостоятельно менял авторизацию; её актуальное состояние нужно проверить, не перезаписывая эти настройки. Инструкция: [Google-вход](google-sign-in.md). Приватный bucket `day-photos` и его RLS добавлены миграцией `day_private_photos` 20 ноября. Текущий Site URL — `http://localhost:3000`; разрешены два точных возврата: `http://localhost:3000/auth/callback` и `http://localhost:3000/auth/callback?recovery=1`. Это локальные настройки; production URL, публикация Google и реальные проверки входа остаются условиями релиза.

1. Выберите отдельный проект для staging и примените обе миграции из `supabase/migrations/` официальным Supabase CLI (`supabase link`, затем `supabase db push`). Перед изменением существующего production-проекта сделайте резервную копию БД. Не сбрасывайте production-БД командой reset.
2. В Auth URL Configuration задайте реальный HTTPS Site URL и разрешите `/auth/callback`, включая используемый recovery URL `/auth/callback?recovery=1`. Адреса локального теста и production задаются отдельно. Не используйте широкие wildcard для production redirect URL.
3. Настройте email/password, подтверждение email и доставку писем. Проверьте письма во внешнем почтовом ящике, ссылки, срок действия и возврат в нужный домен.
4. Для Google настройте провайдера в Supabase и Google OAuth. В Google укажите callback Supabase, в Supabase — callback приложения. Google Client Secret остаётся в Supabase, не в приложении.
5. Проверьте на двух собственных тестовых аккаунтах A/B: A создаёт записи и дожидается статуса автоматического сохранения; B не видит эти записи в интерфейсе и не может читать/менять их через таблицы/RPC со своим токеном. Проверьте также связь задач/повторений, привычек/отметок, питания/ингредиентов и AI-квот. Не используйте service-role key для проверки RLS: он обходит ограничения.
6. На двух устройствах/профилях A проверьте загрузку и сохранение копии, конфликт ревизий и сохранность локального черновика. Убедитесь, что незавершённый запрос не переносит данные между A/B при переключении.
7. Проверьте Google, email-регистрацию, подтверждение адреса, вход, выход, знакомство нового аккаунта, восстановление/смену пароля и просроченную/некорректную ссылку. Проверьте блокировку cookies/прерванную сеть: приложение должно сообщить о проблеме и сохранить локальные записи.
8. Только на специально созданном тестовом аккаунте проверьте удаление: отмена подтверждения ничего не удаляет; подтверждённый запрос удаляет нужного пользователя и связанные облачные данные; чужой аккаунт недоступен для удаления. Повторите со сменой аккаунта во время подтверждения/запроса.

Отмечайте эти пункты выполненными только после реальной проверки размещённой версии. Unit-тесты и заполненные ключи не заменяют её.

## 4. AI и ограничения беты

Проверьте доступность модели в целевом OpenAI-проекте, лимиты расходов и наблюдение за ошибками без записи личных сообщений/фотографий в логи. Авторизованный тестовый пользователь должен получить ответ на короткий запрос; гость не должен обходить авторизацию. Проверьте включённый/выключенный флажок дневной сводки, отмену запроса и повтор после сетевого сбоя. Дневная сводка передаётся только по выбору пользователя.

Проверьте серверную квоту 10 запросов за 10 минут на пользователя, ограничение размера текста/фото, неподдерживаемый тип файла и отказ внешнего сервиса. Фото отправляется провайдеру только после явного нажатия «Распознать». Gemini предлагает приблизительные нутриенты для видимой порции; проверенная база нутриентов не подключена. Результат требует ручной проверки, неизвестные показатели заполняются пользователем. Бесплатная квота и обработка изображений зависят от проекта Google: [настройка food AI](food-ai.md). Автоматического перехода на платный сервис нет. Текстовый Day AI продолжает использовать отдельный ключ OpenAI.

Day AI остаётся **бетой**: советы и предложения плана доступны при настроенных сервисах. Изменение задач помощником, голос и фото в чате, Web Push и серверная доставка напоминаний пока не реализованы. Обещания в карточках, onboarding и описании релиза должны соответствовать этому состоянию.

## 5. Production-запуск и smoke-check

Нужен хостинг с поддержкой серверного Next.js и HTTPS; статический экспорт не поддержит auth/API. На сервере или в отдельной среде сборки после установки переменных:

```sh
npm ci
npm run release:check -- --strict
npm run verify
cp -r public .next/standalone/
cp -r .next/static .next/standalone/.next/
PORT=3000 HOSTNAME=0.0.0.0 node .next/standalone/server.js
```

Используется `output: standalone`. Перед запуском передайте серверные секреты как переменные процесса средствами хостинга/контейнера; standalone-сервер не читает `.env.local` из исходного родительского каталога. В Docker статические файлы копируются автоматически, `.env*` исключены из build context. Локальную проверку исходников выполняли на Node 20.20.1; контейнер Node 24 ещё требует своей проверки в staging.

Порт/проксирование задаются инфраструктурой. Настройте HTTPS, корректный публичный origin, перезапуск процесса при сбое, доступность и безопасные логи. Не публикуйте сервер разработки. Не включайте сервисные секреты в образ/архив исходников, публичные логи или клиентские файлы.

На production-сборке проверьте:

- Главную, календарь, задачи и повторения, привычки, воду/питание, фокус, завершение дня с переносом и повторное редактирование итогов. Обновление страницы сохраняет записи.
- Пустое пространство, существующие записи, поиск, мобильную навигацию, клавиатуру/диалоги, светлую/тёмную тему и уменьшение движения. Фото, перестановка и скрытие блоков работают прямо на главной.
- Экспорт JSON, предпросмотр импорта, отмену, подтверждение, ошибочный/слишком большой файл и скачивание предыдущей копии после замены. Тестируйте восстановление только в отдельном браузерном профиле с тестовыми данными.
- Аккаунт и Day AI по live-проверкам выше. Публичные файлы доступны; API/auth-ответы имеют `Cache-Control: no-store`.
- PWA на HTTPS: иконка/manifest, установка, обновление со старого service worker, обычный старт с сетью и offline fallback. В открытом приложении можно работать с локальными записями; холодный offline-запуск всех разделов не обещается. API, auth и личные ответы не должны попадать в Cache Storage.

## 6. Данные, резервные копии и откат

Аватар настраивается в профиле: JPEG, PNG, WebP или GIF размером до 5 МБ. Статичное фото обрезается по центру в квадрат размером до 512 × 512 и перекодируется без исходных метаданных. GIF сохраняет исходные кадры и допускается при размере до 512 × 512, количестве до 120 кадров и суммарном бюджете пикселей кадров до 16 777 216; файл проверяется декодером браузера перед сохранением. При уменьшении движения показывается неподвижный кадр. Для гостя аватар хранится локально. Для аккаунта аватар, фон, фотографии блоков/навигации и значки дней загружаются в приватный bucket `day-photos` Supabase. После успешной загрузки UUID входит в облачный manifest; на другом устройстве файл скачивается приватно и кэшируется в IndexedDB. Незавершённая синхронизация видна в настройках, локальный файл сохраняется при отсутствии сети. JSON не содержит бинарные фото или их облачные ссылки.

В настройках доступны русский, английский и итальянский языки. Выбор сохраняется в настройках текущего пространства, входит в JSON и автоматически сохраняемую облачную копию аккаунта и сразу меняет интерфейс, даты и формат чисел. Пользовательские названия задач, заметки и категории не переводятся. Day AI получает выбранный язык для ответа и названий распознанных продуктов; это требует подключённого AI-сервиса. В smoke-check проверьте все три языка, сохранение выбора после обновления и неизменность пользовательских записей.

Записи хранятся в браузере отдельно для гостя и каждого аккаунта. Изменения аккаунта автоматически отправляются в облако после паузы 900 мс. Сохранение сериализуется, состояние dirty переживает перезагрузку, повтор происходит при возвращении в окно/подключении сети. Более новая облачная ревизия подхватывается только при отсутствии локальных изменений. При конфликте сохранение останавливается: нужно экспортировать локальную копию и явно восстановить облачную. Автоматического слияния нет. Локальный сброс не удаляет облачную копию. Если она существует, защитный флаг переживает перезагрузку и блокирует автоматическую отправку опустошённого пространства до явного восстановления или импорта. Ожидающие загрузки фотографии сохраняют локальные ссылки при получении более свежих облачных записей. Гостевые записи/фото и ещё не загруженные изменения могут быть потеряны при очистке данных сайта; следите за статусом синхронизации.

Импорт валидирует файл, показывает сводку и заменяет записи только после подтверждения. Перед заменой создаётся предыдущая локальная копия. После импорта скачайте её в профиле, если нужен откат, и импортируйте как обычный JSON. Хранится одна предыдущая копия на пространство; следующая операция восстановления может её заменить. Это не внешняя резервная система. Фото и завершённое знакомство текущего устройства не заменяются импортом. После JSON-импорта записи аккаунта ожидают автоматической синхронизации; при конфликте ревизий требуется явное разрешение. Восстановление из облака также восстанавливает облачные ссылки на фотографии. Предыдущие версии файлов остаются приватными для совместимости с другими устройствами и удаляются при удалении аккаунта.

Для отката размещения сохраните предыдущий артефакт, lockfile и схему/копию БД. При критической ошибке переключите трафик на предыдущую совместимую версию и перезапустите её; не выполняйте откат SQL или очистку браузерных данных вслепую. Проверьте совместимость сохранённых данных и нового service worker, затем повторите smoke-check. Исправление в UI не должно требовать очистки записей пользователя.

## 7. Что должен определить владелец перед публичным доступом

Нужны реальный домен и хостинг, ответственный за выпуск, канал поддержки и сообщения об ошибках, условия доступа к бете, политика конфиденциальности с фактическим оператором, провайдерами, целями/сроками хранения и порядком удаления данных. Учитывайте передачу добровольно отправленного текста/фото внешним сервисам. Эти сведения не выдуманы и пока не заменены шаблонной юридической страницей.

Публикуйте бету после прохождения проверок на размещённой среде, настройки поддержки и согласования фактических правил обработки данных. Текущий локальный кандидат не означает, что эти внешние условия уже выполнены.
